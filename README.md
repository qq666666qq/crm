# B2B CRM 服务端（开发中）

FastAPI + PostgreSQL 模块化服务原型。客户端和 Agent 必须通过 HTTP API 操作；本项目不提供 Agent 直连数据库的接口。

本服务面向本地开发。首次正式部署前仍需完成安全审查、HTTPS 配置和备份恢复演练。

## 启动

1. 安装并启动 Docker Desktop。
2. 将 `.env.example` 复制为 `.env`，设置强随机数据库密码，并同时更新 `DATABASE_URL` 中的密码。URL 中的特殊字符需要百分号编码。
3. 执行 `docker compose up --build -d`。服务启动时执行 Alembic 迁移。
4. 执行 `docker compose exec api python -m app.bootstrap`，交互式创建首个租户和管理员。密码不会显示在命令行参数中。记录输出的租户 UUID。
5. 访问 `http://127.0.0.1:8000/docs` 查看 API 文档；`GET /health` 检查数据库连接。

Compose 只将 API 绑定到本机，数据库不发布宿主机端口。示例密码仅用于提示，不可用于正式环境。首次初始化后不要重复创建初始租户。

## API 调用约定

`POST /api/v1/auth/login` 接收邮箱和密码，返回随机 bearer token。此 token 只在服务端以 SHA-256 摘要保存，有过期时间和撤销状态。之后每次请求提供 `Authorization: Bearer <token>` 和 `X-Tenant-ID: <租户 UUID>`；租户选择并非授权，服务端仍会检查用户、企业和成员状态。`POST /api/v1/auth/logout` 撤销当前 token，该接口只需 bearer token，用户尚未选择企业时也可退出。

所有公司和联系人写请求必须带 `Idempotency-Key`（1–128 字符）。同一个租户、用户和 key 的原始方法、路径、查询字符串和请求体必须完全一致；重试返回原结果，内容不一致返回 409。请求体按字节比较，所以重试时应原样发送。更新请求包含 `expected_version`；删除时用查询参数 `expected_version`。读取默认不返回软删除记录。

销售员只访问自己负责的公司及其联系人。管理员访问本租户全部数据；经理访问自己及直属、间接下属负责的数据。上下级通过成员管理设置，现有成员迁移后默认为无上级。请求中不可传入 `tenant_id` 或 `user_id`；`owner_id` 可由管理员设置为本租户启用的成员；经理只能分配给自己及其下级，销售员只能设置为自己。`X-Operation-Source` 和 `X-Agent-Run-ID` 是客户端自报的审计元数据，不能证明请求由 Agent 发起。

管理员使用 `GET /api/v1/members` 列出成员，`POST /api/v1/members` 创建新本地账号并加入本租户，`POST /api/v1/members/attach` 使用已有账号 UUID 加入本租户，`PATCH /api/v1/members/{id}` 调整角色和成员状态。最后一名有效管理员不能被停用或降级。账号密码必须通过安全渠道交付；此本地机制不包含邀请、密码重置或用户同意流程。成员接口中的 `user_id` 仅用于指定要加入的已有账号，不用于认证或指定请求主体。

删除后可通过 `POST /api/v1/companies/{id}/restore` 或 `POST /api/v1/contacts/{id}/restore` 恢复，JSON 中提供删除后的 `expected_version`。恢复联系人要求公司仍有效；若渠道已被其他活跃联系人使用，恢复返回冲突。`GET /api/v1/companies/duplicates?name=...&country=...` 返回有权查看的名称和国家相同的疑似重复项，不自动合并。相同域名属于确定性冲突，同公司活跃联系人使用相同标准化邮箱、电话或 WhatsApp 标识会返回冲突，需人工确认。

官网以主机名去掉 `www.`、转小写后，在租户活跃公司范围内唯一。这是第一版假设，不适合多个独立公司共用网站的情况。公司名不唯一。电话要求国际 E.164 格式。公司有活跃联系人时不能删除；删除联系人后才可以删除公司。

## 测试

在安装依赖的 Python 环境运行 `python -m pytest -q`。数据库测试需要设置 `TEST_DATABASE_URL` 指向**专用测试 PostgreSQL 数据库**，测试会创建并删除随机命名的 schema；例如 PowerShell：

```powershell
$env:TEST_DATABASE_URL='postgresql+psycopg://test:test@localhost:5432/crm_test'
python -m pytest -q
```

未设置时数据库测试会明确显示 skipped。不要把生产数据库用于测试。

## 第二阶段业务接口

线索、商机、跟进任务和沟通记录接口使用 `/api/v1`，完整请求结构见 `/docs`。列表支持 `limit`（1–100）、`offset`、状态或阶段和相关业务对象筛选。所有写操作继续要求 `Idempotency-Key`；线索、商机、跟进任务和沟通记录的更新、删除及适用的状态变更要求 `expected_version`。金额和数量在 JSON 响应中以十进制字符串返回，避免浮点精度损失。

创建线索时必须随请求提交至少一条 `evidence`。`evidence_type=quote` 必须提供 `original_quote`；`evidence_type=manual` 必须使用 `source_type=manual` 并提供 `manual_note`。若提供 `quote_start` 和 `quote_end`，两者使用 Python Unicode 字符下标，起点包含、终点不包含，并且必须精确匹配快照。服务端可以校验快照与引用的一致性，但无法独立证明快照来自真实消息，也不能凭客户端自报的来源判断操作者实际是人还是 Agent。相同租户、来源类型、来源消息 ID 与相同原文或人工备注会被拒绝；同一消息可以保留不同引用。

线索按 `new → working → qualified → converted` 流转，也可从未转化状态标记 `disqualified`，通过 reopen 回到 working。`POST /leads/{id}/convert` 要求当前线索为 qualified、有产品意向或需求备注。调用者可提供 `company_id` 关联现有公司，或提供 `company_new` 创建公司；两者都未提供时使用线索已关联的公司。可选的 `contact_id` 和 `contact_new` 分别用于关联或创建联系人；未提供时沿用线索已关联的联系人。每组选择互斥，已有线索关联与请求不一致时拒绝。关联联系人会作为主要联系人加入新商机。新公司名称与同租户现有公司存在疑似匹配时返回冲突，官网域名及联系人渠道冲突也会阻止创建；系统不自动合并。转化时同公司同名称的活跃商机会被视为需人工确认的重复候选；公司相同但名称不同的商机可以共存。公司、联系人、商机、线索状态和成功审计在同一事务内提交。

商机在 discovery、quoting、negotiating 之间可前进或回退；won 和 lost 通过专门接口关闭，关闭后不能普通编辑或改变阶段。lost 必须提供原因，阶段变化在审计的 `changes` 字段中记录旧值和新值。多个联系人可以同时设为主要联系人，但必须属于商机的公司。

`/follow-up-tasks/due` 默认返回当前用户截止现在已到期的待办，可传带时区的 `from_at` 和 `until` 限定时间范围；`/overdue` 查询截止当前时刻的逾期待办；`/reminders` 查询提醒时间已经到达的待办。时间输入必须包含时区，服务端按 UTC 存储。完成和取消是独立状态操作；活动记录的是已发生的沟通，与跟进任务可选关联。活动记录编辑和删除使用版本校验。

销售员对新线索和商机仅可访问自己负责、且关联公司也可访问的记录；任务仅访问分配给自己的记录，活动仅访问自己创建且关联对象可访问的记录。管理员可访问本租户全部记录，经理可访问本人和下级负责的记录。删除已有公司、联系人、线索、商机或任务时，若存在受保护的活跃关联记录，服务端拒绝删除；原始证据随线索保留。

## 备份与恢复

本地可定期执行 `docker compose exec -T db pg_dump -U crm -d crm > crm-backup.sql`，将输出保存到受限访问、独立于数据库卷的位置；生产应设置自动化、保留周期、异地副本和加密。账号与库名若已修改，应使用对应配置。备份包含客户资料，请严格限制访问。

恢复演练应先创建独立空数据库，再用 `psql` 将备份导入该空库，并验证迁移版本、记录数量与业务查询。不要直接覆盖现有业务数据库。当前没有自动备份任务，也尚未执行正式环境恢复演练。

## 已知缺口和上线前工作

- 团队范围按企业成员上下级关系计算；尚未实现跨团队共享授权。
- 登录具备账号失败锁定，但尚无跨进程的入口限流或 OIDC/PKCE；正式部署需要可信身份服务、HTTPS、密钥管理和安全审查。
- 成功操作审计和业务写入同一事务；已认证的失败写请求尝试在独立事务记录结果。数据库故障时失败审计可能无法保存，未认证请求没有关联业务审计主体。来源由客户端声明；不记录字段值，日志也不是防篡改存储。
- 数据备份及恢复演练尚未实施。正式部署必须配置备份、恢复演练、日志脱敏、连接和超时监控。
- 迁移降级会删除数据，禁止对正式数据随意执行 downgrade。
- 不应将开发用 API 直接暴露公网；正式部署还需安全加固及审查。

## Electron 客户端与增量同步

先完成服务端迁移到 `0008` 并启动服务。客户端的代码逻辑验证使用 `npm test`，包含同步合并与模拟主进程会话测试。安装 Node.js 后，在 `client` 目录运行 `npm install` 和 `npm run dev`；构建后可用 `npm run build`、`npm start` 启动。默认连接本机 `http://127.0.0.1:8000`，可通过环境变量 `CRM_API_URL` 指定服务端；非本机地址必须使用 HTTPS。登录令牌仅驻留 Electron 主进程内存，应用退出后需重新登录。

客户端登录后通过 `/api/v1/auth/tenants` 选择企业。服务端在业务写入和审计的同一事务中写入同步事件；客户端通过 `/api/v1/sync/events` 接收变更，断线使用事件游标恢复。每个服务进程使用一个共享监控器批量检查连接状态和事件表；有变化时再按用户权限读取和分发事件，不会为空闲连接逐个轮询事件表。事件过期、删除或权限相关变化会清除缓存并重新检查权限；普通断线会重新读取数据，保留编辑草稿。字段版本冲突由用户选择保留内容。事件只包含经过当前权限校验的数据。

管理员可通过 `/api/v1/sync/status` 查看本租户事件数量和最早时间。可按运维计划执行 `python -m app.sync --retention-days 30` 清理过期事件；清理后离线过久的客户端会重新加载数据。应将事件表、数据库连接池及同步延迟纳入监控。

本机一次测试中 500 个同步连接建立成功，创建一家公司后的变更送达全部 500 个有权接收的订阅者，同时 500 个客户列表请求全部成功（中位约 3.5 秒，95% 约 5.5 秒）；这是少量数据、单租户、单进程、本机测试，不代表生产容量。普通请求每进程最多 8 个同时进入处理，超出部分排队；事件读取最多 6 个同时进行，留出数据库连接供共享监控使用。部署多个进程时，每个进程都有自己的监控器和数据库连接池；上线前应核算所有进程的数据库连接总数，并使用真实数据和持续写入负载复测。商机看板与工作台各列首次加载 20 条，向下滚动可继续加载。关联对象可按名称搜索并分页加载。线索转化界面可选择已有公司或创建公司，并可创建有邮箱的联系人；其他联系人选择方式可通过 API 使用。成员设置支持列出、创建、调整角色和启停成员。

客户端当前边界：分页使用 offset；SSE 通知后会重新获取已加载页面并按 ID 去重，但分页期间发生数据变动仍可能短暂出现缺项，后续事件重取会修正。负责人姓名随已获授权的记录返回；成员列表对管理员开放全企业范围，对经理仅开放本人及其下级。账号设置支持修改密码；不提供修改邮箱、成员邀请或 Agent Runtime。沟通记录使用 version 控制并发，更新和删除必须传入 expected_version；旧客户端需要同步升级。

## 注册、审批与密码找回

配置 `SMTP_HOST`、`SMTP_PORT`、`SMTP_SENDER`，必要时设置 `SMTP_USERNAME` 和 `SMTP_PASSWORD`；服务端通过 SMTP STARTTLS 发送一次性验证码。没有配置时注册和找回密码不可用；不要将真实凭证提交到仓库。本地测试使用模拟邮件服务，尚未验证真实邮件投递。验证码仅保存摘要，30 分钟过期且只能使用一次。注册时填写企业 ID，邮箱验证通过后由企业管理员在成员审批页面决定是否加入并设置角色及上级。已有账号可登录后使用企业 ID 提交加入申请。密码变更和重置会撤销账号在所有企业的现有登录会话。

邮件发送发生在数据库事务提交前；如果邮件已投递但数据库提交失败，验证码可能无法使用，应重新申请。注册及找回密码接口的限流目前是每个服务进程内存级别，进程重启会重置，多进程并不共享；正式公开部署需要在可信入口实施跨进程限流与监控。登录失败达到阈值时账号会暂时锁定，找回密码可解除锁定。现有系统统一将登录邮箱转为小写，沿用既有比较规则。

`0008` 只修改已有 users、tenant_memberships 和 activities 表：新增邮箱校验/重置相关字段、成员上级和活动版本。旧沟通记录版本回填为 1；旧客户端调用沟通记录更新或删除时须新增 `expected_version`，否则将被拒绝。原有经理若未设置上下级，无法继续查看其他成员的私有客户；管理员应在成员管理页面配置上下级关系。
